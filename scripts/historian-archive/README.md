# Shahpur historian backfill

This is the verified backfill stage. Each uploaded batch has a SHA-256 digest, an independent gzip recovery file and a receipt containing the Sheet ID and row range. Checkpoints allow a stopped run to resume with the same directory and cutoff. Historical records are preserved as JSON, including fields that are absent from the current SCADA type definitions.

1. Inspect the production project, verify its identity and deploy the cleanup guard and migration. Confirm the deployed export function rejects cleanup actions and that the direct cleanup cron is gone.
2. Use a private folder in the intended Google account. Deploy `Code.gs` as an Apps Script web app. Set `ARCHIVE_FOLDER_ID` and `ARCHIVE_SECRET` through Script Properties. Set the same secret and the deployed `/exec` URL (`ARCHIVE_SCRIPT_URL`) on the backup host. Treat the secret as a server credential.
3. Set `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` in the backup host's secure environment. Use a recovery directory on company-controlled storage, outside the repo, with restrictive access. Execute one process per directory. Start with a small time window in a test folder.

```powershell
node scripts/historian-archive/backup.mjs '<recovery-directory>' '<ISO-cutoff>'
```

The cutoff is exclusive. An optional third argument is the inclusive start, and the optional fourth argument selects a source table. Use a separate directory for each distinct time window. A missing source table, API failure, count discrepancy or readback checksum failure stops the run. Keep the receipts with the recovery files. Use a new reconciliation run to capture late or updated source rows.

For each catalog entry with a file path, the tool also backs up the original export object locally by SHA-256 and sends base64 chunks to a separate `export_files` workbook. To restore from Sheets, group by export ID and file SHA-256, sort by chunk index, decode and concatenate, then check file length and SHA-256. A missing object stops the backfill for reconciliation.

## Owner-run pull

The owner-only Google deployment remains private. `Pull.gs` runs in Apps Script and pulls bounded pages from `historian_archive_page` using a dedicated credential. It can run without an external caller to the Google web app.

After approval, apply the scoped Supabase migration. Run `prepareArchivePullCredential` in Apps Script and provision the emitted SHA-256 digest in `historian_archive_private.credential`. Keep the raw credential in Script Properties. Set `SUPABASE_ARCHIVE_URL`, `SUPABASE_PUBLISHABLE_KEY` and `ARCHIVE_SOURCE_STARTS` using the independently verified end of the existing backup for each of the three supported tables, `historian_logs`, `historian_aggregates` and `alarms`. The next pull starts at that exclusive boundary. Run a fixture verification first, then run `archivePullRun` and install its five-minute trigger via `scheduleArchivePull`.

The pull worker compares each source window's checksum with the pages verified in Google Sheets. Raw windows end at a five-minute boundary at least ten minutes old. For hourly aggregates, the worker waits until ten minutes after the hour closes so it can capture the rows generated by the hourly job. If the source changes during a read, the worker rewinds the same interval, keeps any unverified pages out of the receipt, and writes a replacement in a fresh workbook part. The worker advances only after verifying the receipt. Export file bytes and the separate recovery copy must also be verified before cleanup. Verify SCADA history, trend and Excel access before removing any source records.

The raw historian worker records the exact Sheet range for each verified window, including windows spanning a month boundary. Empty windows are recorded so readers can distinguish covered periods with zero records from gaps in the archive. To extend the SCADA read manifest, export the private `pull_verification` workbooks in chronological order as Sheets API JSON with `spreadsheetId` and `values`.

```powershell
node scripts/historian-archive/extend-read-manifest.mjs --gzip '<audited-base.json>' '<receipt-values.json>'
```

Use the output as the next read manifest after verifying that the configured SCADA reader can load it and return the original rows. The read manifest does not replace the independent cleanup receipt or authorize deletion.

## Restore historian readings from Sheets

Use a private Sheets API values export for one entire historian recovery grid or worker workbook. Supply the independently verified source count. Both formats check all batch SHA-256 values and counts, then require unique record IDs and the full expected source count before writing a new compressed JSON Lines file.

```powershell
node scripts/historian-archive/restore-sheet.mjs recovery '<values.json>' '<expected count>' '<recovery.jsonl.gz>'
```

`audit-raw.mjs` reads all dashboard recovery ranges using private Google OAuth, compares each date's count and batch checksums with the dedicated Supabase verifier, and writes and reopens independent gzip files. Use the JSON from `verified-raw-manifest.mjs` as the input manifest and an existing company-controlled recovery directory outside the repository as the destination. The command prints the final receipt only after all windows match. This audit covers raw readings through the supplied manifest cutoff.

## Verified raw cleanup

After production SCADA history, trend and Excel checks pass, use the final JSON receipt from `audit-raw.mjs` and the same recovery directory to prepare one window at a time. `preview` emits a read-only count and checksum query. After the approved cleanup is ready to run, `delete` emits a transaction that locks candidate rows, rechecks their fingerprint and rolls back if the affected count differs. The script prints SQL for review. Running the script itself makes no database changes.

## SCADA archive reader

`read-historian-archive` requires an existing SCADA session. Set `HISTORIAN_ARCHIVE_SHEETS` to the single-line output of `extend-read-manifest.mjs --gzip`. The command also accepts the audited base receipt by itself and checks the compressed result against Supabase's per-secret limit. The reader accepts an uncompressed JSON array for small deployments. Each entry has `spreadsheetId`, `range` (A1 notation), `format` (`recovery` or `worker`), `start` (inclusive), `end` (exclusive), `count`, and `sourceDigest` (the source SHA-256 of the ordered batch digests). Keep the read-only Sheets OAuth client ID, client secret and refresh token in function secrets named `HISTORIAN_GOOGLE_CLIENT_ID`, `HISTORIAN_GOOGLE_CLIENT_SECRET` and `HISTORIAN_GOOGLE_REFRESH_TOKEN`.

The reader accepts `start`, `end`, `offset`, `limit`, optional `tagIds`, `sections`, `assets`, `excludeTagIds`, `snapshotsOnly` and `ascending`. It returns exact records, the filtered count and the verified intervals that intersect the request. Instrument trends, the History table and Excel use the archive for configured historical intervals and Supabase for newer intervals. These paths still require production end-to-end acceptance before cutover.

Leave `VITE_HISTORIAN_ARCHIVE_START` and `VITE_HISTORIAN_ARCHIVE_CUTOFF` unset until the contiguous archive range is verified in production. Set both as ISO instants when ready. The start is inclusive and the cutoff is exclusive. A trend spanning the cutoff reads the archive below the cutoff and Supabase from the cutoff onward. A missing coverage interval surfaces as a load error. Ranges with verified zero source rows can appear in the manifest with `count: 0`.

For a dedicated Google service account, enable the Sheets API in its project and grant the account Viewer access only to the private archive folders and workbooks needed by SCADA. Store its credentials JSON as the server-only `HISTORIAN_GOOGLE_SERVICE_ACCOUNT` secret. The backend requests the `spreadsheets.readonly` scope and does not impersonate an account owner.

## Private read cache

Seed the cache from the independently audited recovery receipt and its gzip files. Use the Shahpur project ref and supply the authorized management token through the process environment.

```sh
node scripts/historian-archive/seed-read-cache.mjs '<audited receipt.json>' '<recovery-directory>' '<project-ref>'
```

The seeder requires a private bucket, verifies every uploaded object by reading it back, and updates the archive manifest only after all objects match. The Edge Function verifies each cached file against the manifest before using it. On a cache miss or failed integrity check, it reads the original private Google Sheet. No client read or write policy is required for this bucket.
